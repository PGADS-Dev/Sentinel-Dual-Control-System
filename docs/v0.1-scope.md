# Sentinel v0.1 Scope

## Purpose

Sentinel v0.1 is the first narrow implementation step toward the Sentinel v1 technical proof.

It is not a complete product, a polished platform, or a broad engineering showcase.

Its purpose is to define a small, credible, reviewable proof of fault-aware embedded behavior.

## Core goal

Sentinel v0.1 establishes the core logic needed to show that a small distributed embedded system can:

- detect abnormal conditions explicitly
- make deterministic decisions
- transition through clear operating states
- enter degraded or fail-safe behavior intentionally
- expose its behavior through observable traces

The value of v0.1 is not feature count. The value is clarity.

## In scope

Sentinel v0.1 includes:

- common worker state definitions
- common worker event definitions
- common worker fault definitions
- deterministic worker state transition logic
- mandatory fault scenario definitions
- minimal architecture documentation
- state machine documentation
- fault matrix documentation
- observability requirements documentation
- supervisor simulation placeholder documentation

The future dual-worker STM32 hardware setup, CAN communication, Raspberry Pi supervisor implementation, physical fault injection, and trace capture pipeline are roadmap items. They are documented to preserve direction, but they are not required for the current v0.1 skeleton.

## Operating states

The required operating states are:

- `INIT`
- `NOMINAL`
- `DEGRADED`
- `FAIL_SAFE`

Each state must have a clear purpose and clear transition rules.

## Mandatory fault scenarios

Sentinel v0.1 defines these mandatory fault scenarios:

1. Loss of heartbeat from one worker
2. Incoherent peer state between workers
3. Communication loss on CAN or equivalent loss of exchange

Optional scenarios may be added later only if they directly strengthen the proof and do not delay the main scenarios.

## Proof deliverables

Sentinel v0.1 must produce:

- one architecture document
- one state machine document
- one fault matrix
- one observability document
- one proof deliverables checklist
- one clear out-of-scope boundary

## Out of scope

Sentinel v0.1 does not include:

- full STM32 hardware integration
- full CAN implementation
- complete Raspberry Pi supervisor implementation
- physical fault injection hardware
- blackbox trace capture pipeline
- polished dashboard
- web interface
- mobile app
- OTA update pipeline
- rollback system
- cloud connectivity
- Bluetooth or Wi-Fi features
- advanced HMI
- advanced Linux crash pipeline
- complex tooling
- persistent database
- multi-node scaling

## Success criteria

Sentinel v0.1 is successful when:

- the system goal is written clearly
- in-scope and out-of-scope boundaries are explicit
- operating states are fixed
- mandatory fault scenarios are fixed
- observability expectations are fixed
- proof deliverables are listed
- no additional feature is added unless it strengthens the central fault-handling proof

## Final statement

Sentinel v0.1 is a focused starting point for proving responsible embedded behavior under fault.

Everything in v0.1 must support one message:

Detect faults, decide deterministically, degrade intentionally, fail safely, and make the behavior observable.
